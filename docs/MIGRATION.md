# Xenofactions migration architecture and support matrix

The original `xenofactions` repository remains the 1.7.10 behavioral authority. This repository keeps the ExampleMod build islands and is intentionally limited to Forge 1.7.10 and Forge 1.16.5. No Stonecutter, source preprocessing, generated native source merger, new framework or runtime common library is used.

## Architecture

Each `versions/<minecraft>` project owns its loader, Minecraft types, registries, commands, events, packets, world access, persistence binding and client code. Its pinned wrapper and `target.json` remain unchanged. The root configures only `common` and aggregate launch/build tasks. Shared version allocation, release output, archive verification and IntelliJ conventions remain in `build-logic`/`scripts`.

`common` contains three unchanged original types: `com.hfr.clowder.FactionRole`, `FactionMemberRecord` and `com.hfr.tdm.BlockAreaEdges`. The native membership reader and editor use the same role values and block-edge conversion as 1.7.10. These sources have no Minecraft/Forge imports. Other apparently similar legacy code is not forced into common.

The native 1.16.5 save bindings own their state through the overworld `DimensionSavedDataManager`. They do not call the 1.7.10 implementation. Unported fields are retained as opaque NBT at the persistence boundary rather than deleted or interpreted as implemented gameplay. The editor owns a bounded map record snapshot; its server session checks operator level 4, player life/dimension, expiry, map equality, container identity and server-issued token before accepting a GUI action. All packet work reaches the owning thread through `enqueueWork`. Wand points come from block interaction events, not custom client-supplied coordinates. No background world mutation is introduced.

1.7.10 retains the registered `hfr` IDs, packet discriminator ordering, configurations, data loaders/migrations and complete resources. Its only modified production source is `RefStrings`: correct Xenofactions display name, generated release version, and removal of a stale config GUI factory reference whose class is absent from the original sources. The three common extractions preserve exact class packages and contents. Loader metadata now states Xenofactions, the selected version and minimum Forge dependency. Build-only JourneyMap/NEI dependencies are not bundled or made runtime requirements.

## Major native API replacements

| 1.7.10 binding | 1.16.5 foundation binding | Semantic boundary |
| --- | --- | --- |
| `cpw.mods.fml @Mod` pre/init/post/server events, separate buses | Forge `@Mod`, mod event bus, Forge lifecycle/player/command events | Client init registered only on physical client; per-server session cleanup |
| `GameRegistry` item/block and numeric registries | `DeferredRegister`/`RegistryObject` | Wand retains the exact `hfr:item.world_border_wand` registration; other blocks/entities are pending |
| `EntityPlayerMP`, `World`/`WorldServer`, `DimensionManager` ints | `ServerPlayerEntity`, `ServerWorld`, server overworld and resource-key dimensions | Integer dimensions retained only at the persistence compatibility boundary; explicit mapping for writes |
| `NBTTagCompound`, `WorldSavedData`/`MapStorage` | `CompoundNBT`, native `WorldSavedData`/`DimensionSavedDataManager` | Same logical file names/root fields; no silent projection of unported fields; malformed existing data blocks replacement |
| `getEntityData` persisted player context / clone | Forge player persistent data / PlayerEvent.Clone | Preserve durable context, never carry session authority across lifecycle changes |
| `CommandBase` sender/op checks | Brigadier, `CommandSource.hasPermission` and player `hasPermissions` | Inspection subset only; level 3 administration vs level 4 editor preserved |
| `SimpleNetworkWrapper` with discriminators | Direction-bound `SimpleChannel` and `enqueueWork` | Native foundation protocol is separate; no claim of cross-Minecraft network compatibility; server never accepts client map/position ownership |
| `IGuiHandler`, server container/client GUI | `ContainerType`, `NetworkHooks.openGui`, native `ContainerScreen`, client `ScreenManager` | Native editor has no inventory slots or kit lease until inventory migration is ready |
| LWJGL key codes/client proxy | Client-only Forge registration/GLFW F10 binding | Actual current F10 behavior retained; Right Alt/overlay renderer pending |
| Forge `Configuration` + resource language files | ForgeConfigSpec TOML + modern JSON language/item model/pack format 6 | Legacy gameplay settings are not faked as supported native config; old `.lang` stays 1.7.10-only |
| Legacy map API/reflection paths | No native integration binding yet | Core builds without optional map APIs; modern dependencies must be established before porting |

Forge references: [native saved data](https://docs.minecraftforge.net/en/1.16.x/datastorage/worldsaveddata/) and [SimpleImpl/main-thread packet handling](https://docs.minecraftforge.net/en/1.16.x/networking/simpleimpl/). Actual source compilation validates the selected pinned mappings/API signatures; documentation alone does not establish runtime behavior.

## Minecraft acceptance procedures

Report the target/JAR, Forge and Java versions, exact command/action, expected versus observed behavior, and relevant log/stack trace for each failure. Keep 1.16.5 acceptance in a separate test world; do not replace your production 1.7.10 server with the foundation artifact.

### 1.7.10 reference acceptance

1. Start a Forge 10.13.4.1614/Java 8 dedicated test server with the migrated production JAR, first without optional integrations. Report startup/mod discovery, command availability and any missing client/API classes. Repeat with your actual optional-mod set.
2. Load a copy of an existing save/config. Verify faction/member/rank UUIDs, cities/capital/home, claims/permissions, maps/modes/spawns, kits, shop IDs/links and terminal ownership. Restart and report any data loss or unexpected migration.
3. Test faction founding and initial capital, leader-only capital changes/cooldown, capital-only `/c sethome`, Officer+ terminal placement, one-active-terminal rule and recovery after deleting/replacing a terminal. Confirm no automatic Builder Contract award.
4. Check XShop normal-player trading versus explicit level-3 management, rename-safe links, disabled/admin-only/faction visibility flags and stale menu rejection.
5. Open the editor with F10 or `/tdm editor gui`; test inventory kit save/cancel/restoration, real block wand corners versus air clicks, logout/death/dimension invalidation, context reopen, maps disabled for voting and per-mode spawns. Check TDM, neutral FFA and Search and Destroy separately. Optional JourneyMap/Dynmap checks must confirm public boundary/sites without admin editor state and the independent Right Alt world/fallback toggle.

### 1.16.5 foundation acceptance

1. Start a fresh Forge 36.2.34/Java 8 dedicated test server with the native JAR and no map mods. Expect the foundation startup log and `config/xenofactions-foundation.toml`. Join with a matching client; verify hfr discovery, no dedicated-server client-class crash, `/c list` and `/xc foundation` output.
2. As a level-4 operator, run `/tdm map create spaceship`, then `/tdm editor gui spaceship` or F10. Expect a native bounds-only editor. A non-operator must be refused editor/admin commands.
3. Choose Use wand. Select A/B using actual negative-coordinate blocks and confirm air clicks leave points unchanged. Reopen and Save bounds; expect half-open X/Z display that includes the selected maximum block. Reopen/restart to verify saved bounds and last selected map. Inventory contents must remain intact.
4. Begin another selection and Cancel; old saved bounds must remain unchanged. Repeat with logout, death, dimension change, permission revocation, five idle minutes or server restart; the previous draft/token must not authorize a save. A copied wand without a session must never select or alter blocks.
5. Optional controlled logical-data check: copy only `hfr_clowder.dat` and `xenofactions_tdm.dat` from a stopped 1.7.10 test save into the separate native world's `data/`. Inspect `/c list`, `/c info <faction>`, `/xc cities` and map list. Re-save one map's bounds and confirm the backup appears and unrelated map/faction fields survive. Unknown custom dimension mappings must be rejected for editing until configured. Test malformed data only on disposable copies; it must not be overwritten with an empty store.
6. Expect no faction creation, claim protection, match simulation, kits, shops, full editor pages, map overlays or optional integrations in this native build. Those remain subsequent migration work, not failed acceptance of an advertised feature.

## Remaining blockers and uncertainty

There are no observed compile/packaging/archive-verification blockers for either target. The clean milestone is a complete 1.7.10 source/resource baseline plus the bounded native 1.16.5 save/editor foundation.

Further work includes native faction/city/player gameplay and external JSON loaders; version-specific items/block-state and inventory migration; actual modern JourneyMap/Dynmap/other compatibility dependency selection; native renderer/world-generation architecture; and runtime acceptance of both artifacts. The original old-machine/weapon/fallback branches need deeper behavior audits before native ports. Original optional `jarWithEarthMaps` and development identity build conveniences were not copied; existing Earth resources use normal target packaging, and native development uses the template's tasks. None of these differences alters the copied 1.7.10 gameplay implementation.
