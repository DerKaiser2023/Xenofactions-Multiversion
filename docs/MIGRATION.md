# Xenofactions migration architecture and support matrix

The original `xenofactions` repository remains the 1.7.10 behavioral authority. This repository keeps the ExampleMod build islands and is intentionally limited to Forge 1.7.10 and Forge 1.16.5. No Stonecutter, source preprocessing, generated native source merger, new framework or runtime common library is used.

## Architecture

Each `versions/<minecraft>` project owns its loader, Minecraft types, registries, commands, events, packets, world access, persistence binding and client code. Its pinned wrapper and `target.json` remain unchanged. The root configures only `common` and aggregate launch/build tasks. Shared version allocation, release output, archive verification and IntelliJ conventions remain in `build-logic`/`scripts`.

`common` contains three unchanged original types: `com.hfr.clowder.FactionRole`, `FactionMemberRecord` and `com.hfr.tdm.BlockAreaEdges`. The native membership reader and editor use the same role values and block-edge conversion as 1.7.10. These sources have no Minecraft/Forge imports. Other apparently similar legacy code is not forced into common.

The native 1.16.5 save bindings own their state through the overworld `DimensionSavedDataManager`. They do not call the 1.7.10 implementation. Unported fields are retained as opaque NBT at the persistence boundary rather than deleted or interpreted as implemented gameplay. The editor owns a bounded map record snapshot; its server session checks operator level 4, player life/dimension, expiry, map equality, container identity and server-issued token before accepting a GUI action. All packet work reaches the owning thread through `enqueueWork`. Wand points come from block interaction events, not custom client-supplied coordinates. No background world mutation is introduced.

1.7.10 retains the registered `hfr` IDs, packet discriminator ordering, configurations, data loaders/migrations and complete resources. `RefStrings` adapts the display name, generated release version and absent config GUI factory reference. `CityCenterRelocationManager` includes the current main-repository fix preserving homes that remain inside relocated city territory. The three common extractions preserve exact class packages and contents. Loader metadata states Xenofactions, the selected version and minimum Forge dependency. Build-only JourneyMap/NEI dependencies are not bundled or made runtime requirements.

Native faction operations are owned by `FactionService`, with `FactionSavedData` as the single native storage binding. Commands call this service on the server thread; no native path calls legacy classes. Member authorization uses canonical `FactionMemberRecord` UUID/role data, or explicit NAME/AUTO name authority. `PlayerLifecycle` owns per-server timer state, backed by world-root JSON through `PlayerTimers`. Faction updates retain opaque root and per-faction fields, including when record indices change after disband. Known legacy member/leader/officer fields mirror canonical mutations. Rename updates name-based territory/diplomacy references without changing UUIDs; disband releases stored territory ownership, clears matching terminal registrations and removes known relationship references. Unported external builder/wall-art stores are untouched and must resolve missing faction UUIDs safely when their native services are implemented.

`FactionGameplay` implements city/territory, capital/home, relationships, treaties, tribute, accounting and building hooks directly against that same store. It is the native authoritative implementation, with name-based legacy fields mirrored only at the save boundary. `FactionRuntime` owns transient confirmations, war administration toggles, merge offers, delayed travel and a revision-invalidated read view. Commands, events and tile entities run on the server thread. `CityCenterTile`, `ConquestTile` and `WarpTentTile` supply the minimal real world lifecycle; `CityCenterContainer` validates native menu actions against fresh leader authority, city identity, dimension, life and distance. Placement accounting waits until Forge placement cancellation has completed. Relocation checks placement/break events explicitly and restores world/state/token on failure.

`FactionEvents` binds only the protections found in the reference: player break/place/use, origin-based explosion protection, safezone damage/healing/projectiles, visitor permissions, bankruptcy, build-grace return behavior, enemy kill rewards and faction/public chat. There is no invented blanket piston/fire/bucket/entity protection or default friendly-fire rule. The inventory Debug item is the explicit protection bypass; operator, creative and Officer status alone do not bypass territory checks. Possession of a selection wand grants no authority. `EditorSessions` handles both existing level-4 map bounds and level-3 faction zone selections without introducing an Earth exemption implementation.

Territory generation uses Java truncation `(x + 1) / 16, (z + 1) / 16`; block lookup uses `x / 16, (z + 1) / 16`. These deliberately differ from vanilla chunks, especially around negative coordinates. City radii remain strict circles sampled at 16-block offsets, while the reference rectangular administrator selector uses floor-divided endpoint cells. `TerritoryKey` preserves these separate paths. Conquest-only provider cells are marked explicitly and never become cities/capitals.

Native `BorderFeedback` runs after travel on the server tick, using the reference popup's truncated player coordinates and Z-minus-one lookup independently of protection queries. Its transient per-player dimension/zone/faction/city identity suppresses repeated popups and seeds silently on login/respawn; logout and server stop discard it. Nearby exposed stored-cell edges retain the reference geometry, colors and one-in-three particle cadence. A dimension-tagged client packet delivers five-second flag/city/prestige popups, the original crossing sound and rising firework particles through the client queue. Client world changes clear popup state; Right Alt toggles particles independently of notifications. Protocol `foundation-2` requires matching client/server builds. Native registered player content uses the Xenofactions Creative tab; the server-issued selection wand retains its legacy hidden status. Flag blocks are non-opaque, and cloth samples world light at its raised position while retaining faction-tinted base textures and untinted overlays.

No automatic chunk, item, player or mod registry migration is performed. Use selected logical NBT and supported timer/moderation JSON in a separate 1.16.5 test world. Unknown custom dimension IDs require an explicit mapping; import never guesses identity or dimension values. Existing logical claims may be inspected/protected without city blocks; world-dependent upgrade/transfer/relocation requires the matching real native tile and fails if it is absent.

Disband backs up/prevalidates faction data, persists penalties first, commits the native faction edit, then requests a native saved-data flush. This prevents a failed cooldown write from granting a penalty-free disband, but JSON and Minecraft saved data are not a single crash-atomic transaction: an abrupt failure between writes can leave a creation penalty with the faction still present. Other faction mutations use normal native dirty-save timing. A normal stopped-server restart remains a required acceptance check.

## Next coherent migration block

Accept the new native core faction platform before expanding into shops/terminals or matches. Explicit pre-UUID binding still requires a deliberate identity policy. Shops/terminals, kits/matches and their editor/voting/HUD integrations remain separate future blocks. A saved TDM enabled flag remains inert and never blocks membership; the eventual native match engine must enforce the live reference membership guard.

## Native faction gameplay handoff (2026-10-09)

The initial membership/timer slice and bounds editor have user-confirmed runtime results for creation, comrades, disband, cooldown clearing and map persistence/editing in heavily modded 1.16.5. The subsequent core city/claim/war/economy/chat port is implemented natively but **NEEDS RUNTIME ACCEPTANCE**. ### Networking, GUI and optional dependencies

Faction operations use ordinary server command dispatch and server lifecycle/PvP events; no custom faction packet or client-owned membership state is introduced. The existing `hfr:foundation` channel/protocol `foundation-1` retains `Action` (message 0, client to server) and `Snapshot` (message 1, server to client). `Action` uses `enqueueWork` and revalidates operator level 4, life, dimension, expiring server token, map snapshot and container identity through `EditorSessions`. ### Compatibility decisions

- Native applications use the existing UUID `identityApplications` schema and survive restart. The reference command still uses its transient legacy name set; this persistence gap is corrected in the native workflow without editing main.
- Canonical role authority keeps a single Leader. Native kicking refuses the Leader instead of reproducing the reference's missing owner guard, which can remove the only owner. The previous Leader becomes an Officer on `/c owner`.
- Online acceptance can find the applicant across server dimensions rather than depending on the administrator's current world lookup. UUID mode never resolves authority by a reused name, and ambiguous NAME-mode membership is refused.
- Imported pre-UUID staging remains loadable and retained, but grants no role authority. The reference mentions a migration binder without implementing one; this slice does not guess UUIDs or perform online profile lookups. Factions with canonical members require a stable faction UUID and one valid owner.
- Native names allow 1–80 printable characters after the same whitespace/quote normalization; MOTDs are bounded to 1,024 characters. The reference does not impose these bounds. Creation in custom dimensions requires an explicit legacy mapping so stored coordinates remain interpretable.
- New-player protection keeps the actual legacy distinction between the disabled-by-default config module, transient server toggle, UUID PvP grace and retained `keepInvUntil` field. No inventory retention is added. Timers continue through logout, respawn and normal restart without being cloned or renewed; enable the runtime toggle again after restart to enforce remaining grace.
- Malformed canonical faction data or timer JSON fails closed instead of skipping identities or replacing the store with empty data. Existing source files are preserved and backed up before writes. Unported Minecraft items, chunks, entities and compatibility hooks remain outside logical-data migration.
- Active wars and declaration timestamps are explicitly read back by the reference, so native logical wars resume after restart. Administrator declaration/check/legacy-mode toggles restart disabled. Enemy markers remain one-way UUID relationships with independent 72-hour removal and kill rewards; ending a declared war does not erase them. The twelve-hour offline defender exception belongs to conquest/list-war raid eligibility, not ordinary enemy container breaking/use.
- The shared home/rally setting cooldown uses a ten-minute wall clock. The reference's nominal 600-second counter is decremented from its territory/world tick loop; native timing deliberately removes tick-rate and loaded-dimension dependence. Travel retains horizontal-movement cancellation without inventing damage cancellation, and adds native collision/fluid/world-border/footing checks.
- A receiving Leader must accept a merge; the reference lacks that acceptance-rank check. Merges preserve UUID members, joined timestamps, unresolved staging names, cities, accounting and collision-renamed warps without normal disband penalties. Conquest provider cells remain distinct from city identities to avoid false capital candidates.
- Public chat keeps the reference's two lines, prestige title and Gold Leader/Blue Officer/Dark Green Citizen colors. Faction/alliance channels retain role/display-name formatting. Native `/cc mute/unmute` filters server recipients coherently rather than depending on the legacy client packet's stale server mute tag. Ignore lists preserve the reference's public/direct-message boundary; they do not filter faction/alliance chat.
- Native building dependencies are limited to city/conquest flags, Warp Tents, Foundation/Asphalt and Officer Chests. Their relevant accounting/recipes/ownership are implemented; the tent uses a minimal native multiblock visual. Built-in flag patterns use retained textures. Custom image flags and unrelated production buildings stay opaque/pending. The commented-out City Center recipe is not resurrected.
